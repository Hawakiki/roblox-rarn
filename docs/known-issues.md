## 🔴 RN-1 · `install` 이 남의 디렉터리를 지운다 (데이터 손실)

**상태:** 미수정. 이것 때문에 `v0.1.0` 릴리스를 철회했다 (2026-08-21).

### 무슨 일이 일어나나

`rarn install` 은 `packageDir` 이 가리키는 디렉터리를 **자기가 만든 것인지 확인하지 않고**
통째로 교체한다. 그 자리에 사용자의 소스가 있으면 사라진다. 경고도, 확인도 없고,
"installed N packages" 라는 성공 메시지가 뜬다.

### 재현 1 — 문서화된 명령 두 개, 플래그 없음

```bash
# packages/my-lib/init.luau 와 packages/my-lib/README.md 가 있는 프로젝트에서
rarn import      # packageDir: "Packages" 를 쓴다
rarn install     # packages/ 가 사라진다
```

```
설치 전:  packages/my-lib/init.luau
          packages/my-lib/README.md

설치 후:  packages/Promise.luau
          packages/_Index/evaera_promise@4.0.0/promise/init.lua
```

윈도우와 macOS 는 파일시스템이 대소문자를 구분하지 않으므로 `Packages` 와 `packages` 가
같은 디렉터리다. 그리고 조사 결과 **`packages/` 는 실제로 존재하는 유일한 모노레포 형태**의
소스 디렉터리 이름이다 (Wally 사용 저장소 614개 중 약 25개, 생태계에서 별이 가장 많은 코드들).

### 재현 2 — 대소문자와 무관한 일반형

```jsonc
{ "packageDir": "src" }   // 손으로 적으면
```

`rarn install` 이 `src/` 를 지운다. 즉 근본 원인은 대소문자 충돌이 아니라 **소유권 검사의 부재**다.
대소문자는 사고가 *우연히* 일어나는 경로일 뿐이다.

### 왜 이렇게 됐나

| 결정 | 어디 | 무엇을 놓쳤나 |
|---|---|---|
| `import` 가 `packageDir: "Packages"` 를 쓴다 | M13, `src/import/wally.ts` | 이주하는 프로젝트의 Rojo 파일이 이미 `Packages` 를 가리키므로 맞춘 것. 판단은 옳았으나 대소문자 무시 파일시스템에서 `packages/` 와 충돌하는지 확인하지 않았다 |
| realm 디렉터리를 통째로 교체한다 | M6, M12, `src/linker/swap.ts` | 원자적 교체를 만들면서 "교체 대상이 우리 것인가" 는 묻지 않았다 |
| `assertSafePackageDir` | `src/linker/layout.ts` | `.` 과 경로 구분자는 막지만 "이미 존재하는 남의 디렉터리" 는 막지 않는다 |

### 수정 방향

> **Rarn 이 만들지 않은 디렉터리는 지우지 않는다.**

realm 디렉터리는 언제나 `_Index/` 와 `-- Generated by Rarn` 헤더가 붙은 shim 을 갖는다.
그렇게 생기지 않은 디렉터리를 만나면 **거부하고 무엇을 확인해야 하는지 말한다.**

이 규칙 하나로 두 재현 경로가 모두 막히고, 앞으로 나올 변종도 막힌다. 대소문자만 특별 처리하면
재현 2 가 남는다.

관련 파일: `src/linker/swap.ts`, `src/linker/layout.ts`, `src/import/wally.ts`

### 노출 범위

`v0.1.0` 은 2026-08-21 11:22Z 에 공개되어 12:59Z 에 철회됐다. 자산 다운로드는 4회였고
그 전부가 검증 과정에서 발생한 것으로 설명된다 (릴리스 자산 3개 일괄 다운로드 1회씩,
`rokit install` 실사용 재현으로 윈도우 +1). **외부 유입 흔적 없음.**

태그 `v0.1.0` (`569b97b`) 는 남겨 두었다 — 배포는 철회했지만 그 커밋이 0.1.0 이었다는 이력은
사실이다.

## 🟠 RN-3 · `dedupe` 가 같은 DataModel 안의 중복을 놓친다

**상태:** 미수정. R2 종합(Agent 9)이 **대조군과 함께 재현**했다고 보고. 나는 직접 재현하지 않았다.

보고 내용: 범위가 정확히 한 버전에서 교차하는 두 요구자가 `3.2.0` 과 `3.2.1` 로 갈려 한
DataModel 안에 ModuleScript 두 개가 되는데, `rarn dedupe` 는 양쪽 모두에서
"no duplicates — every package is installed at exactly one version" 이라고 답한다.

즉 **제약 5 가 금지하는 바로 그 호환 중복을, 제약 5 를 위해 만든 진단이 이상 없다고 선언한다.**

R2 는 이것이 워크스페이스 이전에 **단일 매니페스트 안에서도 이미 새고 있다**고 본다
(`docs/research/r2-workspaces.md` §3.5). 고치기 전에 직접 재현할 것.

## 🟠 RN-4 · `place` 파생이 실제로 흔한 형태에서 무력하다

**상태:** 미수정. R2 Agent 2 가 저장소 844개 프로젝트 파일을 조사해 보고.

`src/project/place.ts` 는 루트 `default.project.json` 만 읽는데, 조사한 멀티 place 저장소
30개 중 **25개가 그 파일을 갖고 있지 않다** (다른 이름의 프로젝트 파일을 쓴다). 따라서 M14 의
place 파생과 unmounted-realm 경고가 하필 그 형태에서 동작하지 않는다.

R2 는 라이브러리형 프로젝트 파일(`tree.$path` 만 있는 것)에서도 unmounted-realm 경고가
침묵한다는 것을 별도로 보고한다 — `place.ts` 가 그 형태를 `scanned: false` 로 처리하기 때문.
