## 고쳤고, 아직 출하 안 됨

**여기 있는 것은 아무에게도 닿지 않았다.** 0.2.0 을 받은 사람은 이 절의 결함을 그대로 갖고 있다.
다음 릴리스에서 이 절이 통째로 아래로 내려간다.

- **RN-14** — `rarn cache clean` 이 터미널 아닌 stdin 에서 질문만 찍고 아무것도 지우지 않은 채
  **exit 0** 으로 끝나던 것. RN-8 과 같은 모양이고, 질문을 하는 나머지 한 명령에 있었다.
  답이 없는 질문은 영영 끝나지 않아 이벤트 루프가 마르고, 프롬프트 반 줄만 남는다.
  이제 `RN0004` 로 거절하며 `--yes` 를 알려준다 — `init` 처럼 기본값으로 진행하지 **않는** 것은
  두 방향의 값이 다르기 때문이다. `init` 이 잘못 넘겨짚으면 고칠 수 있는 파일이 하나 생기고,
  여기서 잘못 넘겨짚으면 이 기계의 모든 프로젝트가 다음 설치에 네트워크로 돌아간다.
  상세는 CHANGELOG.
- **RN-15** — `rarn cache verify --json` 이 다이제스트 불일치를 본문에 적고도 **exit 0** 으로
  끝나던 것. 사람용 출력은 같은 상황에서 1 을 냈다. `--json` 은 스크립트가 읽는 쪽이고
  스크립트는 본문이 아니라 종료 코드를 읽으므로, 잡으라고 만든 호출자에게만 조용했다.
  이 명령에서 유일하게 공격일 수 있는 발견이다. 상세는 CHANGELOG.
- **RN-16** — 대소문자만 다른 alias 두 개가 대소문자 무시 파일시스템에서 한 파일이라,
  루트 shim 하나가 다른 하나를 조용히 덮어쓰던 것. **설치는 성공으로 끝나고, `rarn.lock`
  은 정확하며, `doctor` 도 보지 못한다.** 남는 것은 `require(Packages.EnumList)` 가 나중에
  쓰인 쪽을 돌려주는 것뿐이었다.

  별칭 유일성 검사가 문자열을 **대소문자를 구분해서** 비교했다. 파일시스템은 그렇게 하지
  않는다. 이제 접어서 비교하고, 두 철자를 **둘 다 보여 준다** — 눈에 다르게 보이는 두
  이름이 한 파일이라는 설명이 없으면 Rarn 의 버그로 읽힌다.

  [R3](research/r3-performance.md) §5.6 이 카운트를 맞추다 발견했다: `link` 이 shim
  1,136개를 썼다고 보고하는데 디스크에는 1,131개가 있었다. 세 에이전트가 독립 재현했다.
  **RN-1 과 같은 계열이다** — 이름은 NTFS 나 기본 APFS 에서 정체성이 아니다. 상세는
  CHANGELOG.
- **RN-17** — `rarn.lock` 안쪽 맵(`dependencies`·`requestedBy`·`root`)을 OS 로케일로
  정렬해서, 한 파일이 두 순서를 따르고 같은 설치가 머신마다 다른 락파일을 쓰던 것. 이제
  코드 유닛 순서 하나이고, `src` 에 `localeCompare` 가 다시 생기면 테스트가 실패한다.
  상세는 CHANGELOG.
- **RN-18** — `rarn.json`·`rarn.lock` 을 제자리에서 덮어써서, 쓰는 도중 중단되거나 디스크가
  차면 사람이 관리하는 `rarn.json` 이 객체 중간에서 잘린 채 남던 것 (반복 쓰기 중 무작위
  kill 100번 중 35번). 이제 옆 임시 파일에 쓰고 rename 한다. 상세는 CHANGELOG.
- **RN-19** — 로그인 토큰 파일(`~/.rarn/auth.json`)을 기본 모드(보통 0644)로 쓴 뒤에야 0600
  으로 조여, 그 사이 같은 기계의 다른 계정이 토큰을 읽을 수 있던 것(macOS/Linux). 이제 0600
  임시 파일을 rename 으로 덮는다. 읽을 수 없는 토큰 파일은 새 `RN0603` 으로 알린다.
- **RN-20** — 응답 없는 연결에서 요청이 Bun 의 300초 × 재시도(최대 약 15분)만큼 멈추고,
  `login`·`whoami` 가 `--offline` 을 우회해 GitHub 로 나가던 것. 네트워크 입구를 하나로
  모아 오프라인 가드와 30초 응답·무진행 타임아웃(`RN0102`)을 건다. 결과를 모르는 게시는
  "게시됐을 수 있음" 으로 알리고, 토큰 파일은 어디 있든 팩되지 않는다. 상세는 CHANGELOG.
- **RN-21** — 캐시의 zip 이 `rarn.lock` 과 어긋나면 아무것도 받지 않고 레지스트리를 탓하는
  `RN0300` 을 던지던 것(주석은 재다운로드라 했다). 그 조언대로 락파일을 지우면 손상된
  바이트가 고정됐다. 이제 레지스트리에 물어보고, 캐시가 레지스트리와 다를 때만 지운다.
  동결된 M4·M8 기록에는 정정을 덧붙였다. 상세는 CHANGELOG.
- **RN-22** — 레지스트리 메타데이터의 dependency alias 를 검사 없이 `<alias>.luau` 경로로
  써서, `../` 를 담은 alias 로 사용자가 쓸 수 있는 아무 `.luau` 파일이나 덮어쓸 수 있던 것.
  이제 파싱 때 락파일 스키마의 alias 패턴(하이픈 허용)으로 거절한다(`RN0112`). 레지스트리
  전체 alias 45,794 개가 통과한다.
- **RN-23** — 락파일의 `version` 이 검사 없이 캐시·`_Index` 폴더 이름이 되어, 고친
  `rarn.lock` 하나로 캐시 밖의 기존 디렉터리를 재귀 삭제할 수 있던 것(0.2.0·0.1.1).
  락파일 스키마의 `version` 에 semver 패턴을 넣었다 — 스키마 시계가 다시 시작된 이유다.
- **RN-24** — semver 가 못 읽는 레지스트리 버전(`0.0.0-001`)이 있는 패키지는 버전 정렬이
  `TypeError` 로 죽어 모든 명령이 실패하던 것. 이제 그 버전만 뺀다. 상세는 CHANGELOG.

## 고쳤고 출하됨 — 0.1.1

- **RN-1** — `install` 이 자기가 만들지 않은 디렉터리를 지우던 것. 이제 realm 디렉터리가
  `_Index/` 를 갖거나 전부 Rarn 이 생성한 shim 일 때만 교체하고, 아니면 `RN0421` 로 거부한다.
  대소문자 충돌이면 그 사실을 따로 짚는다. `import` 도 같은 충돌을 미리 경고한다. 상세는 CHANGELOG.
- **RN-2** — 하니스가 올바른 교차 realm shim 을 실패로 보던 것. `--mount` 로 형제 realm 을
  등록하면 실제로 검증되고, 마운트가 없으면 실패가 아니라 "not verified" 로 보고한다.
  하니스 테스트가 두 경우를 모두 돌리므로 CI 가 본다. 상세는 CHANGELOG.
- **RN-3** — 한 DataModel 안의 호환 중복을 아무도 보지 않던 것. `dedupe` 의 논리 결함이
  아니라 Rarn 에 place 라는 범위가 없던 것이었다. `src/doctor/places.ts` 가 프로젝트 파일을
  읽어 같은 DataModel 에 들어가는 트리들을 비교하고, `dedupe` 가 보고하고 `install` 이
  호환 중복을 경고한다 (`RN0213`). 상세는 CHANGELOG.
- **RN-4** — `place` 파생이 루트 `default.project.json` 하나만 읽던 것과, 라이브러리형
  프로젝트 파일에서 unmounted-realm 경고가 침묵하던 것. 이제 `*.project.json` 을 3단계까지
  읽고 `$path` 를 파일 기준으로 풀며, 파일을 읽은 것과 거기서 무언가를 찾은 것을 구분한다.
  상세는 CHANGELOG.
- **RN-5** — 해석이 호환 버전으로 갈라져 만족하지 않는 버전을 설치하던 것.
  같은 major 그룹을 합칠 때 살아남는 버전이 흡수한 제약을 전부 다시 검사하고,
  만족하지 못하는 것은 `RN0200` 충돌로 보고한다. 상세는 CHANGELOG.

## 고쳤고 출하됨 — 0.2.0

RN-11 ~ RN-13 은 하니스 결함이라 바이너리에 들어가지 않는다 — 개발용 도구이고, 이 태그의
소스에 들어 있다는 뜻이다. RN-6 ~ RN-10 은 사용자에게 닿는다.

- **RN-6** — 512 KiB 넘는 파일이 든 패키지를 설치할 수 없던 것. Bun 에서 fflate 의 비동기
  워커가 빈손으로 돌아왔다. 해제를 동기로 바꿨다.

  **이것은 한동안 "0.1.1 에서 해결" 로 잘못 기록돼 있었다.** 고침 커밋은 그 태그 **뒤**에 있어
  0.1.1 을 쓰는 사람은 `4x8matrix/class-index@3.0.0` 같은 패키지를 여전히 설치할 수 없고,
  받는 메시지는 `RN0310 ... The download may be corrupt. Try again` 이다 — 아카이브는
  멀쩡하므로 그 조언은 통하지 않는다. 콜드 캐시로 출하본에 대고 재현했다. 상세는 CHANGELOG.
- **RN-7** — `doctor` 가 `:WaitForChild("x")` 로 쓴 require 를 못 읽던 것. 레지스트리의
  JS 포팅 계열이 전부 그 형태라, 올바른 설치에 대고 "선언했는데 안 쓴다" 를 310줄
  쏟아내고 있었다. 네 가지 표기를 한 연산으로 읽는다. 상세는 CHANGELOG.
- **RN-8** — `rarn init` 이 터미널 아닌 stdin 에서 프롬프트 반 줄만 찍고 파일도 메시지도
  없이 끝나던 것. 이제 기본값으로 진행하고 그 사실을 말한다. 상세는 CHANGELOG.
- **RN-9** — `rarn init` 의 Rojo 안내가 프로젝트 파일이 **아예 없을 때만** 침묵하던 것.
  가장 정보가 없는 경우가 유일하게 안내를 못 받았다. 상세는 CHANGELOG.
- **RN-10** — `doctor` 요약이 읽은 파일이 아니라 보고할 것이 있던 패키지의 파일만 세던 것.
  "scanned 212 files across 52 packages" 가 실제로는 444개를 읽은 실행이었다. 상세는 CHANGELOG.
- **RN-11** — 하니스에 `:WaitForChild` 가 없던 것. 레지스트리 대부분이 그것으로 트리를
  탐색하는데 읽기 전용 질의 열 개가 하나도 없었다. 기본 검사는 몰랐다 — Rarn 의 shim 은
  인덱싱만 쓴다 — 대신 `--execute` 가 레지스트리 절반에 안 됐다. 상세는 CHANGELOG.
- **RN-12** — 한 번 실패한 모듈이 이후 계속 `cyclic require` 로 보고되던 것. in-flight
  플래그를 성공 경로에서만 지웠다. 두 줄로 재현된다. 상세는 CHANGELOG.
- **RN-13** — `game` 스텁이 자기 주석과 반대로 하드 에러를 내던 것. 모든 키가 테이블을
  돌려주니 `game:GetService(...)` 가 테이블 호출로 죽었다. 상세는 CHANGELOG.
