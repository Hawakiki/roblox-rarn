# M9 — R3 대응

> 완료 시점의 사실만 담고 이후 편집하지 않는다 — 링크 수정만 예외.

**완료:** 2026-08-23
**결과:** 정합성 결함 1개(RN-16), 최적화 2개 착지, 1개 재고 기각. 506패키지 warm 반복
설치가 출하 바이너리로 **6,352 → 4,024 ms (36.6%)**. 547 → 552 통과.

[R3](../../research/r3-performance.md) 는 조사였고 §8 을 일부러 비워 두었다. 이것이 그
§8 이다. R3 의 R4 권고 7개 중 **1·3·4** 를 처리했다.

---

## 측정 환경

Windows 11 Pro, AMD Ryzen 7 5800X3D (8코어/16스레드), NVMe SSD / NTFS, Bun 1.3.14.
**Windows Defender 실시간 검사 켜짐, 저장소도 작업 디렉터리도 제외 목록에 없다.** 끄지
않았다 — Windows 사용자가 실제로 설치하는 환경이 이것이다.

모든 비교는 **on/off/on** 으로 돌렸다. R3 가 이 설계로 자기 결론 두 개를 뒤집었고, 이번에도
그것 없이는 아무것도 주장할 수 없었다. 캐시는 전부 `RARN_CACHE_DIR` 로 격리했고 개발자의
실캐시는 건드리지 않았다.

## RN-16 — 대소문자만 다른 alias 가 서로를 덮어쓴다

**성능 조사가 카운트를 맞추다 찾았다.** `link` 이 shim 1,136개를 썼다고 보고하는데 디스크에
마커를 가진 파일이 1,131개였다. 다섯이 사라졌다.

별칭 유일성 검사가 문자열을 **대소문자를 구분해서** 비교했고, 파일시스템은 그렇게 하지
않는다. `EnumList.luau` 와 `Enumlist.luau` 는 Windows 와 기본 macOS 볼륨에서 한 파일이다.

증상이 전부 초록이었다는 점이 이 결함의 성질이다 — 설치 성공, `rarn.lock` 정확, `doctor`
못 봄. 남는 것은 `require(Packages.EnumList)` 가 나중에 쓰인 쪽을 돌려주는 것뿐이다.

| 한 파일이 되어버림 | 두 패키지 |
|---|---|
| `enumlist.luau` | `bubshayz/enumlist` → **Enumlist** vs `sleitnick/enum-list` → **EnumList** |
| `bettersignal.luau` | `codedjimmy/bettersignal` vs `howmanysmall/better-signal` |
| `lemonsignal.luau` | `data-oriented-house/lemonsignal` vs `kineticwallet/lemon-signal` |
| `waitfor.luau` | `sleitnick/wait-for` vs `farukcoskn/waitfor` |
| `tableutil.luau` | `sleitnick/table-util` vs `finobinos/tableutil` |

두 철자 다 `deriveAlias()` 가 스스로 만든 것이라 `aliases` 를 안 쓴 사람도 피할 수 없다.
`deriveAlias()` 만 놓고 보면 506개 중 대소문자 무시 시 충돌하는 그룹이 **62개**다.

### 범위를 측정으로 정했다

고치기 전에 "링커의 의존성 shim 에도 같은 함정이 있나" 를 레지스트리 메타데이터
**4,492 버전 / 2,365 의존성 집합**에 대고 쟀다.

| | 결과 | 판단 |
|---|---:|---|
| 한 패키지가 대소문자만 다른 의존성 별칭 둘을 선언 | **0건** | 링커에 검사 추가할 이유 없음 |
| 의존성 별칭 vs 자기 모듈명, 대소문자만 다름 | 19건 | **전부 합법.** 디스크에서 `promise/` 와 `Promise.luau` 는 다른 이름이고(하나는 확장자를 갖는다) Roblox 인스턴스명은 대소문자를 구분한다 |

**방어 코드를 넣지 않은 근거가 측정값으로 남았다.** 고칠 자리는 매니페스트 검증 하나였다.

### 메시지에 넣은 두 가지

```
RN0030: 2 packages in "dependencies" would be installed as 'Enumlist' and
        'EnumList', which are one file on Windows and macOS — filenames
        there are not case-sensitive.
          @bubshayz/enumlist -> Enumlist.luau
          @sleitnick/enum-list -> EnumList.luau
        Give one of them a different name under "aliases", for example:
          "aliases": { "@bubshayz/enumlist": "Enumlist2" }
```

**두 철자를 접힌 형태가 아니라 둘 다 보여 준다** — 눈에 다르게 보이는 두 이름이 부딪혔다는
말은 이유가 없으면 Rarn 의 버그로 읽힌다. 그리고 **제안하는 대체 이름을 그 섹션이 이미
쓰는 별칭들에 대고 확인한다** — 붙여넣으면 같은 에러로 돌아오는 조언은 예시가 없는 것보다
나쁘다.

### 고치자 저장소 자신의 벤치마크가 거부됐다

`test/benchmark/packages.json` 이 같은 다섯 쌍을 그대로 선언하고 있었다. **즉 그 벤치마크는
그동안 다섯 패키지가 서로 덮어쓰는 설치를 재고 있었다.** 파일 순서상 먼저 나온 쪽이 별칭을
지키고 뒤에 나온 쪽이 자기 scope 를 PascalCase 로 앞에 붙이는 규칙으로 풀었다.

설치 파일 수가 7,045 → **7,050** 이 됐다. 그 5개가 그동안 사라지던 shim 이다.

`bun run check` 는 `bench` 를 돌리지 않으므로 CI 도 이것을 잡지 못했다.

## C2 — 은퇴 트리 삭제를 임계 경로 밖으로

`swapIn` 이 방금 은퇴시킨 트리를 그 자리에서 지웠고, 그게 설치의 마지막 동작이었다.
**2,049 ms 전부가 디스크의 트리가 이미 올바르게 된 뒤에 쓰인 시간이다.** 뒤에 아무것도 없으니
겹칠 것도 없었다.

### R3 가 경고한 함정이 실재했다

`clearLeftovers` 를 그냥 비동기로 만들면 **그것이 지우는 `.rarn-tmp` 가 빌드가 쓰는
디렉터리**라 설치를 망가뜨린다. 둘로 갈랐다.

| | 기다리나 | 왜 |
|---|---|---|
| `clearStaging` | **예** | 빌드의 입력이다 |
| `clearRetired` | 아니오 | 아무것의 입력도 아니다 |

`clearRetired` 의 `readdir` 은 시작에 한 번만 돌아, `swapIn` 이 나중에 은퇴시키는 트리는
목록에 없다 — 롤백 밑에서 지워질 수 없다. 실패는 삼킨다: 은퇴 트리가 중단된 실행을 뜻하던
때는 던지는 것이 정보였지만 이제 매 설치마다 하나씩 생기고, Studio 가 파일을 붙잡고 있다고
온전한 설치를 실패시키는 것은 틀린 거래다.

### 측정

| 방법 | 전 | 후 | 절약 | |
|---|---:|---:|---:|---|
| **출하 바이너리** | 6,352.2 | **5,057.1** | 1,295 ms | **20.4%** |
| TypeScript (in-process) | 6,373.7 | 4,381.8 | 1,992 ms | 31.3% |
| TypeScript (프로세스별) | 6,299.3 | 4,292.5 | 2,007 ms | 31.9% |

드리프트 대조 −0.2%, 세 방법 전부 비중첩. 작은 그래프도 같은 모양(in-process, 전부
비중첩): 6패키지 18.4%, 49패키지 29.6%, 52패키지 30.4%.

**바이너리와 TypeScript 의 격차는 설명하지 못했다.** arm A 는 세 방법이 일치하는데
(6,299 / 6,352 / 6,374) arm B 만 바이너리가 765 ms 느리다. JIT 온기는 아니다 — 프로세스별
TypeScript 가 in-process 와 같은 답을 낸다. **바이너리가 사람이 실행하는 쪽이므로 20.4% 가
인용할 숫자이고, 보수적인 방향이기도 하다.**

### 정확성

세 팔의 산출이 동일하다 — 575패키지 / 7,050파일 / 45,757,187 바이트. 출하 바이너리로
직접 확인: 1회차 은퇴 디렉터리 0개, 2회차 1개, **3회차도 1개**(쌓이지 않는다), 트리 동일.

### 비용

디렉터리 하나. 설치 사이에 이전 트리가 함께 남는다 — 506패키지에서 43 MB. `rarn init` 은
이미 두 스크래치 이름을 `.gitignore` 에 넣고 있었고, `publish` 는 `_Index` 모양 탐지에
기대지 않고 이름으로 제외하게 했다. **안전성은 나빠지지 않는다 — 사용자가 갖고 있던 트리가
더 오래 살아남는다.**

## C3a — 캐시에서 꺼내는 복사를 8개씩

복사의 비용은 바이트가 아니라 **파일 단위**다. Windows 에서 파일마다 open·write·close 와
on-access 검사를 물고, 기다리는 동안 프로세스가 할 수 있는 일이 없었다.

| 방법 | 전 | 후 | 절약 | |
|---|---:|---:|---:|---|
| **출하 바이너리** | 5,132.8 | **4,024.3** | 1,108 ms | **21.6%** |
| TypeScript | 4,297.1 | 2,847.5 | 1,450 ms | 33.7% |

드리프트 −1.9%. 49패키지 30.7%, 52패키지 30.6%(둘 다 비중첩). **6패키지는 범위가 겹쳐서
아무것도 주장하지 않는다.**

제약 1 에 대한 안전성은 경로가 보장한다 — 패키지마다 자기 `_Index` 항목 디렉터리에 쓰고,
한 버전으로 해석된 두 패키지는 키로 그 항목을 공유하므로 두 워커가 같은 경로를 노리는 일이
없다.

### 두 절약이 더해진다는 것은 잰 것이다

|  | C2 없음 | C2 있음 | **C2 기여** |
|---|---:|---:|---:|
| **C3 없음** | 6,374 | 4,297 | **2,077** |
| **C3 있음** | 4,873 | 2,847 | **2,025** |
| **C3 기여** | **1,501** | **1,450** | |

단독 합 3,578 ms vs 실제 3,526 ms — 간섭 **−52 ms(1.5%)**.

이 표가 필요했던 이유는 성능이 아니다. **빌드가 빨라지면 C2 의 지연 삭제가 더 이상 그 뒤에
숨지 못할 수 있고, 그러면 C2 가 치른 비용(디렉터리 하나)이 값을 못 하게 된다.** 재 보니 여전히
숨는다.

### 동시성이 결함을 하나 만들 뻔했고, 기존 테스트가 잡았다

`mapWithConcurrency` 가 첫 실패를 즉시 전파하는데 진행 중인 워커는 계속 썼다. 호출자의
정리는 `finally` 에서 도니, 그 사이 워커가 **방금 지운 디렉터리를 다시 채운다** — 실패한
설치가 `.rarn-tmp` 를 남겼다. `finally` 가 막으라고 있는 바로 그 상태이고, M12 시대에 쓴
원자성 테스트가 그대로 잡았다.

헬퍼를 고쳤고 덤으로 하나를 되찾았다.

| | |
|---|---|
| 진행 중인 일을 기다린 뒤 전파 | 정리가 실제로 마지막에 돈다 |
| **가장 낮은 인덱스**의 실패를 보고 (가장 빠른 것이 아니라) | 인덱스는 순서대로 나눠 주므로 실패보다 앞선 것은 끝났거나 자기도 실패했다 → 실행마다 같은 값 |

두 번째 덕분에 CLAUDE.md 가 명시한 *"any failure reports the same package first"* 가
동시성을 넣고도 그대로 남는다.

## C3b — `countFiles`, 재고 기각

R3 는 이 쌍(패키지마다 재귀 walk 두 번)을 **482 ms** 로 값매겼다. 직렬 루프에서는 맞는
값이었다. 동시화한 뒤 같은 프로브로 다시 재니:

| | 시간 | 절약 | |
|---|---:|---:|---|
| walk 둘 다 (현재) | 2,847.5 ms | — | |
| 목적지 walk 만 제거 | 2,807.1 ms | **40.4 ms** | **범위가 겹친다 — 노이즈 안** |
| 둘 다 제거 (천장) | 2,737.9 ms | 109.6 ms | 3.8% |

몫: 캐시 walk 69.2 ms, 목적지 walk 40.4 ms.

고려한 대안 — 캐시 쪽을 한 번만 걸으며 전체 수와 `root.path` 아래 수를 함께 세어 출력을
살리는 것 — 은 정확히 목적지 walk 만 없애는 것이고 **노이즈 바닥도 못 넘는다.**

기능을 통째로 지우면 3.8% 를 얻고, 사용자가 pruning 이 일어났다는 것을 보는 **유일한 줄**을
잃는다. 제약 3 이 적어 둔 Rarn 과 Wally 의 차이가 바로 그 pruning 이다. **어느 쪽도 안 한다.**

측정값은 `countFiles` 바로 옆에 박아 두었다. 이 두 walk 를 낭비로 보고 지우려는 사람이
반드시 나오기 때문이다.

## 배운 것

**상한은 그것을 잰 baseline 에 대해서만 유효하다.** C3b 는 자기를 건드리지도 않은 변경에
값의 **77%** 를 잃었다(482 → 110 ms). R3 §6 에 남은 상한들도 같은 이유로 다시 재야 하고,
그건 재측정 비용이지 R3 의 흠이 아니다 — R3 는 자기가 잰 조건을 적어 두었다.

**최적화를 재는 일이 정합성 결함을 찾는다.** RN-16 은 성능 숫자를 맞추다 나왔고, 이 저장소가
찾은 결함 목록에 같은 종류가 이미 여럿이다. 카운트가 안 맞는 것을 그냥 넘기지 않는 습관이
테스트보다 많이 잡는다.

**절약이 더해지는지는 재야 안다.** C3 가 빌드를 빠르게 만들면 C2 의 값이 사라질 수 있었고,
2×2 없이는 그것을 알 방법이 없었다. 최적화 둘을 각각 재고 끝내면 그 상호작용은 아무도 안
본다.

**동시성은 무해해 보일 때가 가장 위험하다.** 복사 루프를 동시화하는 것은 경로가 겹치지
않으므로 안전해 보였고 실제로 안전했지만, 실패 경로에서 정리와 경합했다. 잡은 것은 새 테스트가
아니라 **한 시대 전에 다른 이유로 쓴 테스트**였다.
