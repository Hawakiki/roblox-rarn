# M16 — 0.1.0 배포 ↩️ 철회됨 (1.0.0 은 M15 뒤로)

**순서를 바꿨다.** 1.0.0 대신 0.1.0 을 먼저 낸다.

M15(워크스페이스)는 이 로드맵에서 유일하게 범위가 불확실한 항목이고, 락파일의 `root`
스냅샷을 건드릴 가능성이 있다. 1.0.0 을 먼저 내면 그 스키마 변경이 릴리스 직후의 버전
범프가 되고, 안 내면 릴리스가 M15 의 불확실성에 인질로 잡힌다.

0.1.0 은 그 딜레마를 그냥 없앤다 — 지금 설치 가능해지고, 안정성 약속은 안 하므로 M15 의
스키마 변경이 공짜다. M16 의 실제 어려운 부분(Rokit 에셋 규칙, 릴리스 파이프라인)은 버전
숫자와 무관하게 여기서 다 만들어지고 검증된다.

그리고 지금 Rarn 에 남은 가장 큰 미지수는 "코드가 맞나" 가 아니라 "쓸 만한가" 다. 전자는
CI·하니스·소스맵·Studio 대조까지 갖춰 답이 나와 있고, 후자는 데이터가 하나도 없다.

#### Rokit 에셋 규칙 — 추측하지 않고 소스를 읽었다

`rokit add` 가 전원에게 실패하는 것이 이 마일스톤의 유일한 실질적 함정이라, 규칙을
rokit 소스에서 직접 확인했다.

| 무엇 | 어디 | 규칙 |
|---|---|---|
| 파일명 → OS | `lib/descriptor/os.rs` | 부분 문자열 `windows` / `macos`·`darwin`·`apple` / `linux`·`ubuntu`… |
| 파일명 → 아키텍처 | `lib/descriptor/arch.rs` | `aarch64`·`arm64` / `x86_64`·`amd64`·`x86-64` … |
| 확장자 | `lib/sources/artifact/format.rs` | zip, tar, tar.gz, tar.xz, gz |
| **아카이브 안의 파일** | `lib/sources/extraction.rs` | 도구 이름과의 일치를 **요구하지 않는다.** 6개 항목(전체 경로·정확한 이름·대소문자 무시 이름·실행 권한·실행 확장자·실행 파일 내용)으로 점수를 매겨 최고점을 고르고, **0점 초과면 후보** 다 |

마지막 줄이 중요하다. 리포 이름은 `roblox-rarn` 이고 명령은 `rarn` 이라 둘이 다른데,
`rarn.exe` 는 실행 확장자와 실행 파일 내용만으로 2점이라 아카이브에 실행파일이 하나뿐이면
이긴다. 사람이 직접 받아 풀었을 때 나오는 이름이기도 하다.

#### 그래서 실제로 돌려 봤다

읽은 것은 읽은 것이지 확인한 것이 아니라서, 버릴 태그(`v0.0.1`)로 릴리스를 만들고
`rokit add` 를 진짜로 돌린 뒤 릴리스와 태그를 지웠다.

| 단계 | 결과 |
|---|---|
| 워크플로 6개 잡 | 전부 초록 |
| 자산 이름 | `rarn-0.0.1-{windows-x86_64,macos-aarch64,linux-x86_64}.zip` |
| `rokit add Hawakiki/roblox-rarn@0.0.1 rarn` | 성공, `rokit.toml` 에 기록됨 |
| `rarn --version` | 동작 |
| 정리 | 릴리스·태그 삭제 완료 |

**두 가지가 나왔다.**

첫째, `rokit trust` 가 먼저 필요하다. Rokit 은 아무도 보증하지 않은 도구를 실행하지
않으므로 첫 설치에서 *"has not been marked as trusted"* 로 멈춘다. Rarn 이 아니라
Rokit 의 정책이고, 기계당 한 번이다. README 와 CHANGELOG 에 넣었다.

둘째가 더 중요하다 — **태그는 v0.0.1 인데 바이너리는 자기를 0.1.0 이라고 말했다.**
`--version` 은 package.json 에서 오기 때문이다. 실험이라 무해했지만, 실제 릴리스에서
태그만 올리고 그 파일을 잊으면 존재한 적 없는 버전을 말하는 바이너리가 나간다.
그래서 release.yml 에 둘이 다르면 **3개 바이너리를 짓기 전에** 죽는 잡을 넣었다.

#### 만든 것

| 항목 | 상태 |
|---|---|
| `.github/workflows/release.yml` — 태그 트리거, check → build ×3 → 초안 릴리스 | ✅ |
| `.github/actions/roblox-tools` — lune·rojo 설치를 ci/release 가 공유 | ✅ |
| `package.json` 0.0.0 → 0.1.0 | ✅ |
| CHANGELOG.md | ✅ |
| README 설치 절 (rokit.toml 우선) | ✅ |
| 에러 코드 범위표 | ✅ |
| 실제 릴리스 | ⏳ |

`private: true` 는 **유지한다.** 애초에 npm 에 발행할 물건이 아니고(Roblox 개발자는 Rokit 을
쓴다), 그 플래그는 실수로 `npm publish` 하는 것을 막는 역할이다. 예전에 이 표에 "private 가
아니어야 한다" 고 적어 뒀던 것은 틀렸다.

릴리스는 **초안으로** 만들어진다. 태그를 밀자마자 공개되는 것보다, 사람이 자산을 눈으로 보고
게시하는 단계가 하나 있는 쪽이 낫다 — 릴리스는 지울 수 있지만 이미 받아 간 사람의
`rokit.toml` 은 지울 수 없다.

#### 1.0.0 의 선행조건

| 선행조건 | 현재 |
|---|---|
| M11 CI 초록 | ✅ |
| 라이브 발행 1회 성공 | ❌ (`--dry-run` 만) |
| M13 import 로 실제 프로젝트 3개 이주 성공 | ✅ |
| 0.1.0 이 실제로 나가고 `rokit add` 가 동작 | ⏳ |
| M15 (또는 R2 의 기각 결론) | ❌ |
| `package.json` 버전이 0.0.0 이 아님 | ✅ 0.1.0 |
| CHANGELOG 존재 | ✅ |
| 에러 코드표가 문서에 노출 | ✅ README 에 범위표 |

라이브 발행은 영구적이지만, scope 는 GitHub 계정명이고 그건 어차피 내 것이다.
`hawakiki/rarn-smoke@0.1.0` 을 한 번 올리면 잃는 것은 없고, 얻는 것은 M10 전체가 실제로
동작한다는 유일한 증거다. M16 을 기다릴 이유가 없는 항목.
